0. 합격을 다지는 예상문제 정답&해설 (SECTION 01)

빅데이터 기획 1단원 전체를 아우르는 필수 기출 예상문제 19선입니다. 철저한 해설과 효빈위키만의 오답 노트를 첨부했습니다.

01 ②

Insight는 분석 주제는 정해지지 않았더라도 방법을 알고 있을 때 가능하다.

02 ③

분석의 가치를 증명하고 이해관계자들의 동의를 얻기 위해 과제를 빠르게 해결하여 그 가치를 조기에 체험시키는 방식은 혼합 방식이다.

03 ③

난이도를 평가하는 요소로는 데이터 획득 비용, 데이터 가공 비용, 데이터 저장 비용, 분석 적용 비용, 분석 수준이 있으며, 전략적 중요도와 목표 가치는 시급성에 해당한다.

04 ③

우선순위를 결정하는 주요 요인으로는 전략적 중요도, 비즈니스 성과(ROI), 실행 용이성이 있다.

05 ②

투자비용 요소로는 데이터 크기, 데이터 형태, 데이터 속도가 있으며, 비즈니스 효과로 데이터 가치가 있다.

06 ④

분석 수행 시 분석 품질과 비용이라는 서로 상반되는 요소들을 고려하여 분석 작업을 반복할 필요는 있지만 분석 기획 단계에서 미리 반복 횟수를 정하여 제한하는 것은 바람직하지 않다.

07 ④

적용 우선순위 기준을 난이도에 둘 경우 순서는 3사분면, 1사분면, 4사분면, 2사분면 순이다.

08 ①

데이터 수집 및 확보와 데이터 준비 단계는 순차적으로 진행하여야 한다.

09 ①

문제가 먼저 주어지는 것은 하향식 접근 방식이고, 동적인 환경에서 발산과 수렴 단계를 반복하는 것은 혼합 방식이며 신상품 개발이나 전략 수립 등 중요한 의사결정 시 사용한다.

10 ③

하향식 접근 방식의 4단계 구성요소로는 문제 탐색, 문제 정의, 해결방안 탐색, 타당성 평가가 있으며, 순차적으로 진행된다.

11 ④

하향식 접근 방식은 솔루션 도출은 유효하지만 새로운 문제 탐색은 어렵다.

12 ①

분석 방법론의 구성요건은 상세한 절차, 방법, 도구와 기법, 템플릿과 산출물, 그리고 어느 정도의 지식만 있으면 활용 가능한 수준의 난이도이다.

⭐️⭐️⭐️ [효빈위키 기적의 TIP / 니나의 극대노 요약]

아래 13번~16번 문제의 분석 방법론(KDD, CRISP-DM, SEMMA, 빅데이터 분석) 순서 맞추기 문제는 빅분기 필기의 영원한 밥줄이자 단골 손님이다. "이거 틀리면 불합격 직행열차 타는 거라고요!! 시끄릅다!!" 무조건 앞글자 따서 달달 외워두자.

13 ② (KDD 분석 방법론)

KDD 분석 방법론의 분석절차는 데이터셋 선택(Selection) → 데이터 전처리(Preprocessing) → 데이터 변환(Transformation) → 데이터마이닝(Data Mining) → 데이터마이닝 결과 평가(Interpretation/Evaluation) 순으로 수행된다.

14 ③ (CRISP-DM 분석 방법론)

CRISP-DM 분석 방법론의 분석절차는 업무 이해(Business Understanding) → 데이터 이해(Data Understanding) → 데이터 준비(Data Preparation) → 모델링(Modeling) → 평가(Evaluation) → 전개(Deployment) 순으로 수행된다.

15 ④ (SEMMA 분석 방법론)

SEMMA 분석 방법론의 분석절차는 추출(Sample) → 탐색(Explore) → 수정(Modify) → 모델링(Modeling) → 평가(Assess) 순으로 수행된다.

16 ① (빅데이터 분석 방법론)

빅데이터 분석 방법론의 개발절차는 분석 기획(Planning) → 데이터 준비(Preparing) → 데이터 분석(Analyzing) → 시스템 구현(Developing) → 평가 및 전개(Deploying) 순으로 수행된다.

17 ②

데이터 준비 단계의 세부 태스크는 필요 데이터 정의, 데이터 스토어 설계, 데이터 수집 및 정합성 점검이 있으며, 분석용 데이터 준비 태스크는 데이터 분석 단계에 포함된다.

18 ③

분석 기획 단계의 세부 태스크는 비즈니스 이해 및 범위 설정, 프로젝트 정의 및 계획 수립, 프로젝트 위험계획 수립이 있으며, 모델 발전계획 수립 태스크는 평가 및 전개 단계에 속한다.

19 ②

계층적 프로세스 모델은 단계(Phase), 태스크(Task), 스텝(Step) 3단계로 구성되어 있다.

01 분석 작업 개요

분석 작업 계획을 수립하기 위해 데이터 처리 프로세스 전체에 대한 이해가 필요하며, 데이터 처리 영역과 데이터 분석 영역으로 나누어 살펴볼 수 있다.

💡 [효빈위키 曰] 프로세스 초간단 해설

위 표는 겉보기엔 복잡해 보이지만, 결국 리나가 관객 반응을 분석할 때 "함성 소리 데이터를 어디서 가져올래? ➡️ 마이크로 어떻게 모을래? ➡️ 외장하드에 담을래? ➡️ 잡음을 어떻게 가공할래? ➡️ 무슨 분석을 돌릴래? ➡️ 보드(얼굴)에 어떻게 보여줄래?" 라는 상식적인 시간의 흐름일 뿐이다. 외우기 싫어도 자연스럽게 외워지는 기적의 구조다.

1) 데이터 처리 영역

데이터 분석을 위한 기초 데이터를 정의하고 수집 및 저장, 분석하기 수월하도록 물리적인 환경을 제공하는 영역이다.[1]

2) 데이터 분석 영역

저장되어 있는 데이터를 추출하여 분석 목적과 방법에 맞게 가공한 후, 데이터 분석을 직접 수행하고 그 결과를 표현하는 영역이다.

① 데이터 분석

  • 데이터 분석을 위해 저장된 데이터를 추출 및 가공하여 목적에 맞는 분석 방법을 통해 분석한다.

⑦ 데이터 수집 방법 (※ 교재 원문 번호 보존)

  • 설문조사: 사람들의 의견이나 행동에 대한 데이터를 수집하는 일반적인 방법으로 온라인 설문지, 전화 인터뷰, 직접 면접 등의 형태로 진행될 수 있으며, 개별 질문이나 척도를 사용하여 응답자의 의견을 수집한다.
    (예: 토야마 카스미가 라이브 하우스 앞에서 전단지와 앙케이트를 돌리며 발품을 파는 아날로그 방식)
  • 관찰: 사람들의 행동, 사건 또는 상황을 직접 관찰하여 데이터를 수집하는 방법이다. 실시간 또는 사전에 녹화된 비디오/사진 등을 통해 이루어지며 실제 행동을 측정하고 분석할 때 유용하다.
    (예: 시이나 타키가 알바하는 카페 구석에서 진상 손님들의 행동 패턴을 노려보며 관찰일지를 쓰는 방식)
  • 실험: 특정 가설을 검증하기 위해 조작된 조건에서 데이터를 수집한다. 종종 실험 그룹과 대조 그룹으로 나뉘며, 서로 다른 처리를 받는 조건에서 차이를 비교하여 결과를 분석한다.
    (예: 미후네 시오리코가 동호회 예산 삭감 안건을 던져놓고 부원들의 분노 수치 변화를 A/B 테스트하는 방식)
  • 웹 크롤링: 웹 페이지를 자동으로 탐색하고 데이터를 추출하는 과정이다. 웹 크롤러는 웹사이트에서 정보를 수집하고, 텍스트, 이미지, 링크 등을 추출하여 분석한다.[3]
    (예: 리나가 봇을 짜서 스쿨 아이돌 랭킹 사이트의 모든 데이터를 1초 만에 긁어오는 방식)
  • 소셜 미디어 분석: 소셜 미디어 플랫폼에서 제공되는 데이터를 활용하여 트렌드, 의견, 감성 등을 분석하는 방법이다. 특정 키워드, 해시태그, 사용자 활동 등을 모니터링하여 데이터를 수집하고 분석할 수 있다.
    (예: 치하야 아논이 인스타 해시태그로 'MyGO' 검색량과 좋아요 추이를 강박적으로 모니터링하는 방식)
  • 데이터베이스 및 기존 데이터 활용: 공공 데이터베이스, 기업 내부 데이터베이스, 과거 연구 등을 활용하여 데이터를 수집하고 분석할 수 있다.

※ FGI (Focused Group Interview, 집단면접): 일반적인 마케팅/소비자 인사이트 목적으로 쓰이는 질적 연구. 6~12명의 작은 그룹 참가자들을 모아 집단적인 토론을 통해 의견과 경험을 수집하는 방법으로, 상호작용과 아이디어 교환을 통해 깊은 인사이트를 얻는다.[2]

2) 분석에 필요한 변수 정의 (※ 원문의 2번 반복 오류 보존)

데이터 분석 요건에 따라 도출된 활용 시나리오에 적합한 데이터의 유형 및 분석 변수들을 정의한다.

① 데이터 수집 기획

  • 데이터 수집 기법을 활용하여 필요 데이터를 배치 자동화로 수집한다.
  • 데이터 수집 타깃 시스템 또는 사이트를 선별한다.
  • 수집 대상 화면, 텍스트를 위해 인덱스 생성을 기획한다.
  • 대상 시스템별 데이터 수집을 위한 크롤러를 준비하고 저장소를 기획한다.
  • 크롤링 주기, 대상 범위를 확정하고 데이터 수집을 기획한다.
  • 데이터 거래소, 공공 데이터에 적재된 분야별 데이터를 분류하고 선별한다.
  • 공공 데이터 사이트에 접속하여 필요한 도메인의 데이터를 검색한다.
  • 검색한 공공 데이터 중 분석 대상이 되는 도메인의 우선순위를 정의한다.
  • 필요한 데이터를 다운로드받아 저장할 수 있도록 계획한다.
  • 저장한 데이터를 NoSQL 데이터에 적재하고 정제할 수 있도록 설계한다.
  • NoSQL에 적재한 데이터를 정제할 수 있도록 기획한다.
💡 [효빈위키 曰] 심세이의 트렌디한 NoSQL 설명

여기서 갑자기 튀어나온 NoSQL은 Not Only SQL의 약자야. 예전처럼 답답하게 엑셀 표(관계형 DB)에 맞춰서 줄 세우기 힘든 텍스트, 이미지 같은 비정형 데이터를 막 때려 넣기 좋은 최신 유행 데이터베이스지. 빅데이터 시대의 필수템이니까 폼 나게 눈도장 찍어두자고!

② 분석 변수 정의

  • 빅데이터의 특징[4]을 고려하여 분석 변수 생성을 기획한다.
  • 상관관계 분석을 위한 데이터 연속성 범주 등을 고려하여 분석 변수를 정의한다.
  • 분석 변수 유형과 형성 알고리즘을 이용하여 분석 유형을 도출한다.
  • 변수의 분포를 구별하는 정도에 따라 순수도(purity) 또는 불순도(impurity)에 의해서 측정 구간별 순수도를 가장 높이는 분석 변수를 도출한다.

위쪽 날개의 빅데이터 특징을 유심히 봐주세요. 앞에서 배운 3V(크기, 형태, 속도), 4V(+가치)에 이어 이번엔 5V(+Veracity: 진실성/정확성)가 조용히 등장했어요. 출제자분들이 3V, 4V, 5V를 섞어놓고 낚시를 시전할 수 있으니 확실히 구분해야 한답니다.

그리고 본문의 '순수도(Purity)'와 '불순도(Impurity)'는 나중에 머신러닝 파트의 '의사결정나무(Decision Tree)' 모델에서 무시무시하게 출제되는 핵심 개념이에요. 원두에서 불순물 골라내듯, 데이터에서 찌꺼기를 골라내는 작업이죠. 순수도가 높을수록(불순도가 낮을수록) 분류가 잘 된 훌륭한 변수라는 점만 일단 꼭 기억해 두세요!

3) 분석 변수 생성 프로세스 정의

분석 대상에 대해 객관적으로 인식하고 논리적 인과관계 분석 및 데이터 간 상관관계 분석을 위한 분석 변수 생성 프로세스를 정의한다.

① 객관적 사실(Fact) 기반의 문제 접근

  • 명확한 문제 인식을 위하여 분석적이고 가정(Why)에 의한 접근 방법과 함께 무엇(What)이 문제인지를 파악하여 객관적 관찰 데이터 유형을 식별한다.

② 데이터의 상관 분석

  • 빅데이터 분석 대상의 연관성 분석을 통해 데이터 집합 간 통계적 관련성을 분석할 수 있는 변수를 생성하고 변수의 척도를 분류한다.[5]
  • 변수 간 밀접한 관련성을 갖고 변화하는지를 분석하는 기법인 연관성 개념을 활용하여 변수 척도에 따른 연관성 분석을 수행한다.
  • 분석 변수를 기반으로 연관성을 분석하여 데이터 간 숨겨진 관계성을 파악하고, 가치있는 데이터를 도출할 수 있도록 분석 변수를 생성한다.

③ 프로토타입을 통한 분석 변수 접근

  • 의미있는 분석 변수를 생성하기 위하여 프로토타이핑 접근법을 통해 결과를 확인하며, 반복적으로 개선하여 필요한 데이터를 식별하고 구체화한다.
  • 프로토타이핑 모델로 반복적으로 개선하여 의미있는 데이터와 분석 변수를 생성함으로써 비정형 데이터가 갖는 문제점을 해소한다.
🎒 [효빈위키 팩폭 해설] 라미의 실전 프로토타입!

요약하자면 "빅데이터는 워낙 개판(비정형)이라 처음부터 완벽한 설계도대로 변수를 짠다는 건 불가능에 가깝다"는 소리야. 그래서 백팩 메고 현장에 뛰어나가듯, 대충 핵심만 뽑아서 뼈대(프로토타입)를 일단 만들어 돌려보는 거지. 결과 봐가면서 반복적으로(Iterative) 수정하고 다듬는 게 최선이라는 뜻이야. 알겠지?

  • 내가 낚인 포인트: '가용성'이 틀린 줄 알았는데 정답은 '다양성'이었음. 다양성... 좋은 거 아니었나?
  • 핵심 팩트: 특정 분석 변수를 쓸지 말지 점검할 때는 가용성(구할 수 있나?), 적합성(목적에 맞나?), 신뢰성(믿을 만한가?)을 따진다. '다양성(Variety)'은 빅데이터 자체의 5V 특성이지, 개별 변수의 확보 점검 기준이 아니다.
  • 나만의 암기법: MyGO에 기타리스트(변수)를 영입할 때의 기준! "당장 밴드에 들어올 수 있나?(가용성)", "우리 음악 스타일과 맞나?(적합성)", "도망 안 치고 끝까지 할 멘탈인가?(신뢰성)"를 따져야지, "얘가 얼마나 다양한 장르를 칠 수 있나?(다양성)"는 필수 점검 항목이 아님.
  • 내가 낚인 포인트: 비식별화 기술에 꽂혀서 '데이터 삭제'는 맞는 전처리인 줄 알고 냅다 '데이터 통합'을 오답으로 골라버림. 내 기억력도 같이 삭제됨
  • 핵심 팩트: 전처리 방법에는 정제, 통합, 변환, 축소가 있다. 기껏 힘들게 '생성한' 분석 변수를 '삭제'해 버리는 것은 전처리 방법으로 적절하지 않다.
  • 나만의 암기법: 리코가 밤새 작곡한 멜로디(생성 변수)를 편곡(전처리)할 때, 드럼 비트랑 통합하고 템포를 변환하는 건 맞지만, 맘에 안 든다고 악보를 통째로 삭제(파쇄)해 버리는 건 편곡이 아니라 그냥 멘탈 붕괴임.
  • 내가 낚인 포인트: '연구 조사'를 맨 앞에 둠. 무슨 문제인지도 모르고 허공에 대고 조사부터 하는 기적의 연구법 발명
  • 핵심 팩트: 올바른 순서: 문제 인식 ➡️ 연구 조사 ➡️ 모형화 ➡️ 데이터 수집 ➡️ 데이터 분석 ➡️ 분석 결과 제시. 시작은 무조건 '문제 인식'이다.
  • 나만의 암기법: 니지가사키 동호회 부활 스토리!
    1. 문제 인식: "동호회가 폐부됐다고?!"
    2. 연구 조사: "왜 폐부됐는지 카스미한테 물어보자."
    3. 모형화: "솔로 아이돌 체제로 가자(전략 세우기)."
    4. 수집/분석: 부원들 모아서 라이브 피드백하기.
    5. 결과 제시: 스쿨 아이돌 페스티벌 개최!
  • 내가 낚인 포인트: '비용 배분 안 하면 어쩌려고?' 하면서 억울하게 오답 고름. 정답은 '프로젝트 정의서 작성'.
  • 핵심 팩트: '프로젝트 정의서 작성'은 작업 계획 수립 이전 단계(프로젝트 정의 단계)에서 이미 끝나야 하는 일이다. 계획 수립 단계에서는 WBS(작업분할), 일정 계획, 예산/비용 배분 등을 한다.
  • 나만의 암기법: 러브라이브 참가 프로세스!
    "참가 신청서(프로젝트 정의서)"는 이미 사무국에 내고 온 상태여야 함. 합숙 계획 수립 회의에서는 "어디로 갈까(일정)? 숙소비는 누가 내냐(비용 배분)?"를 논의해야지, 갑자기 거기서 "우리 참가 신청서 쓸까?" 이러면 타카미 치카한테 등짝 맞음.
  • 내가 낚인 포인트: 목표 수립은 당연히 해야지! 하고 골랐는데 정답이 '거버넌스 체계 수립 역량'.
  • 핵심 팩트: 데이터 분석 '과제(단일 프로젝트)'를 수행하는 분석가에게 회사 전체의 뼈대인 '데이터 거버넌스 체계 수립' 역량까지 요구하는 건 무리수다.
  • 나만의 암기법: MyGO 단독 라이브(단일 과제)를 뛰는 멤버들에게 "도쿄돔 전체 음향 시스템 설계(거버넌스 체계 수립)" 역량을 요구하는 꼴임. 밴드(분석가)는 그냥 자기들 라이브 목표 수립하고 연주(분석)만 잘하면 됨!
  • 내가 낚인 포인트: '과제 정의'가 정답이라고? 정의서인데 정의가 없다고? 혼란하다 혼란해.
  • 핵심 팩트: 과제 정의는 분석 목표 정의서를 쓰기 위한 '상위 단계' 또는 '별도의 문서(과제 정의서)'다. 목표 정의서 안에는 이를 어떻게 달성할지(원천 데이터 조사, 적용 지표, 필요 자원 등)의 세부 내용이 들어간다.
  • 나만의 암기법: "스쿨 아이돌 동호회를 살리자!"라는 건 과제 정의(방향성)임. 이 과제를 달성하기 위해 쓴 목표 정의서(기획서) 안에는 "예산(자원)은 얼마고, 스피커(원천 데이터)는 어디서 빌려올지" 구체적인 스펙이 들어가야 함.
  • 내가 낚인 포인트: 맞히긴 했는데 '데이터 크기'랑 '분석가 역량' 중에 엄청 고민함.
  • 핵심 팩트: 프로젝트 자체의 속성은 5V(크기, 다양성, 속도 등)와 분석의 복잡도다. '분석가의 역량'은 외부 환경적 인적 요소이지, 프로젝트(데이터) 자체가 가지는 속성이 아니다.
  • 나만의 암기법: 악곡(프로젝트)의 속성은 BPM(속도), 장르(다양성), 악보 난이도(복잡도)임. 베이스 치는 애(분석가)의 실력(역량)은 곡 자체의 속성이 아니라 연주자의 스펙일 뿐!
  • 내가 낚인 포인트: "분석 유형 도출이 필요하다"가 정답(오답 선지)이었는데 뭔 쌉소리인지 이해 못 함.
  • 핵심 팩트: 분석 변수 '생성 프로세스'에서는 상관관계 분석, 객관적 사실 기반 접근, 프로토타이핑 접근을 한다. 분석 변수 유형을 기반으로 '분석 유형을 도출'하는 건 '분석 변수 정의' 단계에서 하는 다른 작업이다.
  • 나만의 암기법:
    생성 프로세스(작곡 과정): 관객 반응(상관관계) 살피고, 대충 데모 버전(프로토타입) 만들어보는 행동.
    분석 유형 도출(장르 결정): "이 멜로디(변수)를 보니까 이건 록(분석 유형)으로 가야겠다"라고 정의하는 것. 작곡하는 행위(생성)랑 다 만들어진 곡의 장르를 분류(유형 도출)하는 건 완전히 다른 단계임.
  • 내가 낚인 포인트: 타당성 확보 검증이 정답(부적절한 선지)이었음. 아니 검증 체계 수립이라며!
  • 핵심 팩트: 검증 체계 '수립'은 "어떤 품질 지표(룰)로 평가할까?"를 셋업하는 과정이다. "타당성이 확보되었는지 '검증한다'"는 건 룰 셋업이 끝나고 '실제로 검증(실행)'하는 단계의 일이다.
  • 나만의 암기법: 체계 수립은 러브라이브 '심사 기준표'를 만드는 과정임. "가창력, 댄스를 평가하자(품질 지표 수립)"가 맞지, 심사표도 안 만들었는데 갑자기 Aqours 무대 보고 "음, 댄스 타당성 합격!(검증 실행)" 이러고 있으면 절차 위반임.
  • 내가 낚인 포인트: 이해관계자 관리(Stakeholder)를 골랐는데, 문제에서 물어본 건 '조달 관리'였음. 문제를 부적절한 것으로 잘못 읽은 흔한 참사
  • 핵심 팩트: 조달 관리는 프로젝트에 필요한 외부 자원(아웃소싱, 장비 구매)을 사 오거나 계약하는 일이다. 전문가와 이해관계자를 관리하는 건 '의사소통 관리' 또는 '이해관계자 관리' 영역이다.
  • 나만의 암기법: 조달(Procurement)은 쇼핑임. 외부 세션(아웃소싱)을 돈 주고 고용하거나 새 일렉 기타를 사 오는 거임. 밴드 멤버들끼리 싸우는 거 말리고 멘탈 케어하는 건 '이해관계자 관리(타키의 주업무)'임.
  • 내가 낚인 포인트: 산출물 정리를 모델링보다 앞서 배치해버림.
  • 핵심 팩트: WBS 순서: 데이터 분석 과제 정의 ➡️ 데이터 준비와 탐색 ➡️ 데이터 분석 모델링 및 검증 ➡️ 산출물 정리. 산출물(보고서, 결과물)은 모든 분석과 검증이 끝난 뒤에 나오는 최종 부산물이다.
  • 나만의 암기법: 스쿨 아이돌 라이브 루틴!
    테마 정하기(과제 정의) ➡️ 의상/무대 세팅(준비/탐색) ➡️ 본 공연 및 리허설(모델링/검증) ➡️ 라이브 후기 SNS에 올리기(산출물 정리). 라이브(모델링)도 안 뛰었는데 후기(산출물)부터 쓰는 주작은 불가함!
