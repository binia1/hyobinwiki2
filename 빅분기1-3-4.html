04 분석 프로젝트 관리

3) 분석 프로젝트의 영역별 주요 관리 항목

프로젝트 관리 지침 체계(KSA ISO 21500)에 따라 분석 프로젝트는 총 10개의 관리 주제 그룹으로 구성되어 있습니다. 각 영역별 핵심 포인트는 다음과 같습니다.

① 범위 관리 (Scope Management)

  • 분석 기획 단계에서 명시한 프로젝트의 범위는 분석을 수행하면서 데이터의 형태와 양 또는 적용되는 모형의 알고리즘에 따라 빈번하게 변경되곤 하며 이것은 프로젝트를 지연시키는 중대한 사유가 됩니다.
  • 분석의 최종 결과물이 분석 보고서 형태인지 시스템인지에 따라 투입되는 자원과 범위가 크게 달라지므로 사전에 충분히 고려되어야 합니다.

② 일정 관리 (Time Management)

  • 분석 프로젝트는 초기에 의도했던 모형이나 결과가 쉽게 나오는 경우가 흔치 않으며, 지속적으로 반복하는 과정에서 많은 시간이 소모되곤 합니다.
  • 분석 결과의 품질을 보장한다는 전제하에 Time Boxing 기법을 사용하여 일정을 관리하는 것이 필요합니다.
⏱️ [효빈위키 팩폭 해설] 4호선 다로나의 짤막 상식: Time Boxing

Time Boxing(타임 박싱): 말 그대로 시간(Time)에 상자(Box)를 씌운다는 뜻이에요. 4호선 배차 간격 맞추는 것처럼요! 분석이라는 게 파고들면 끝도 없이 파고들 수 있어서 연구원들 놔두면 1년 내내 논문만 씁니다 "딱 이 기한까지만 퀄리티 뽑고 끝낸다!"라고 데드라인을 박아두는 아주 현실적인 일정 관리 기법이랍니다.

③ 원가 관리 (Cost Management)

  • 외부 데이터를 활용하여 데이터 분석을 수행하는 경우 데이터 구입 및 수집을 위해 많은 비용이 소모될 수 있으므로 사전에 충분한 조사가 필요합니다.
  • 프로젝트를 수행하는 과정에서 목표한 결과를 달성하기 위해 오픈 소스 도구를 사용하지 않고 고가의 상용 도구를 사용하게 될 경우 비용이 증가합니다.

④ 품질 관리 (Quality Management)

  • 분석 프로젝트의 수행 결과에 대한 품질목표를 사전협의를 통해 수립하고 통제하여야 합니다.
  • 프로젝트 품질은 품질관리계획과 품질통제 및 품질보증으로 구성되어 있으며, 이를 잘 나누어 수행하여야 합니다.

⑤ 통합 관리 (Integration Management)

  • 프로젝트 관리 프로세스들을 통합적으로 운영될 수 있도록 관리하여야 합니다.

⑥ 조달 관리 (Procurement Management)

  • 상황에 따라 분석 프로젝트 목적에 적합한 범위 내에서 외부에 아웃소싱을 수행할 수 있습니다.
  • PoC(Proof of Concept)[1]와 같이 지속성이 보장되지 않은 프로젝트는 인프라 구매보다 클라우드와 같은 대여방식을 고려해 볼 필요가 있습니다.
💡 [효빈위키 曰] 1호선 고나미의 현실 조언

PoC를 한마디로 요약하면, "이거 진짜 될지 안 될지도 모르는데 비싼 서버 컴퓨터부터 덜컥 사지 말고, 그냥 클라우드(AWS 등)에서 잠깐 빌려 쓰고 버리세요!"라는 뜻입니다. 예산을 아끼는 아주 현명한 조언이죠.

⑦ 인적자원 관리 (Human Resource Management)

  • 분석 프로젝트는 인적자원과 데이터가 핵심이므로, 프로젝트 수행 전 전문인력 확보와 고용유지 방안을 검토하여야 합니다.
  • 전문인력의 효율적인 운영을 위해 핵심인재의 전문분야와 보유역량 및 수준 등을 관리하고, 프로젝트별 투입 시점과 피로도 등을 종합적으로 관리합니다.

⑧ 위험 관리 (Risk Management)

  • 필요한 데이터가 확보되지 않거나 품질이 보장되지 않을 경우 분석 프로젝트 진행이 어려울 수 있으며, 관련 위험을 식별하고 대응방안을 수립해야 합니다.
  • 데이터 및 분석 알고리즘의 한계로 품질목표를 달성하기 어려울 수 있으며, 전문인력의 이탈로 프로젝트가 중단될 수 있어 대응방안 수립이 필요합니다.
  • 그 밖에 분석 프로젝트 진행 과정에서 발생할 수 있는 위험을 식별하고, 위험을 분석하여 대응방안을 수립해야 합니다.

⑨ 의사소통 관리 (Communication Management)

  • 프로젝트의 원활한 진행을 위한 다양한 의사소통 채널과 모든 이해관계자가 분석 결과를 공유할 수 있도록 시각화와 같은 방안을 마련해야 합니다.

⑩ 이해관계자 관리 (Stakeholder Management)

  • 분석 프로젝트는 데이터 전문가, 분석 전문가, 비즈니스 전문가, 시스템 전문가 등 다양한 전문가의 참여가 필요하며, 이들을 잘 관리하여야 합니다.
  • 프로젝트 관리자는 분석 프로젝트에 영향을 미치는 이해관계자들을 식별하고 관리하여야 합니다.
[효빈위키 曰]
위 10가지 관리는 프로젝트 관리의 표준(PMBOK)입니다. 결국 프로젝트 관리자(PM)는 개발자, 분석가, 경영진 사이에서 치이고 구르며 멘탈을 챙겨야 한다는 눈물겨운 비즈니스 현실을 보여줍니다.(...)

✅ 개념 체크

✔️ 분석 프로젝트 추가 고려사항

Q. 다음 중 분석 프로젝트 진행 시 추가적으로 고려해야 할 내용으로 틀린 것은?
① 분석 결과를 활용하는 측면에서는 Precision, 분석 모형의 안정성 측면에서는 Accuracy가 중요하다.
② 데이터 크기는 데이터가 지속적으로 생성되어 증가하는 점을 고려한다.
③ 분석 모형의 정확도와 복잡도는 Trade off 관계에 있음을 유념해야 한다.
④ 정형, 비정형 데이터와 다양한 시스템에 산재되어 있는 원천 데이터들을 통합하는 방안을 수립해야 한다.

💡 정답 및 해설: ①
해설: Accuracy(정확도)는 모형과 실제값 사이의 차이인 정확도를 측정하는 지표이며, Precision(정밀도)은 모형을 계속하여 반복했을 때 결과의 일관성을 측정하는 지표이다. 분석 결과를 활용하는 측면에서는 Accuracy가 중요하고, 분석 모형의 안정성 측면에서는 Precision이 중요하다. (즉, 보기 1번은 두 단어의 위치가 반대로 뒤집혀 있습니다.)

📝 합격을 다지는 예상문제

01 신뢰성 높은 데이터 분석 모형 개발을 위한 3가지 데이터셋이 아닌 것은?

  • ① Training Dataset
  • ② Verification Dataset
  • ③ Validation Dataset
  • ④ Test Dataset
[효빈위키 曰] Hint: 제가 '개념서(Training) - 모의고사(Validation) - 수능 본시험(Test)'으로 비유해 드렸던 3대장을 떠올려 보세요. V로 시작하는 그럴싸한 가짜 영어 단어(Verification)가 하나 숨어있답니다.(...)

02 외부 데이터를 수집하고자 할 때 고려해야 할 내용으로 적합하지 않은 것은?

  • ① 데이터를 획득하는 데 필요한 비용을 고려하여야 한다.
  • ② 데이터를 제공받기 위한 계약서를 잘 작성하여 모든 법률적 위험요소를 완전히 해소한다.
  • ③ 데이터를 수집하여 저장할 방법을 살펴보아야 한다.
  • ④ 내부 데이터와의 결합 가능여부 등을 검토하여야 한다.
[효빈위키 曰] Hint: 객관식 시험의 절대 진리입니다. 선지에 '모든', '완전히', '무조건' 같은 극단적인 단어가 들어가 있으면 99.9% 확률로 그게 오답(틀린 설명)입니다. 세상에 법적 위험을 '완전히' 해소할 수 있는 마법의 계약서 따윈 없으니까요.

03 데이터 확보 계획 수립 시 분석 변수 점검항목으로 적절하지 않은 것은?

  • ① 데이터 다양성
  • ② 데이터 가용성
  • ③ 데이터 적정성
  • ④ 기술적 타당성
[효빈위키 曰] Hint: Part 1의 점검 항목 분류 표를 기억하시나요? 크게 '데이터 수집(적정성/가용성/대체유무)', '데이터 적합성', '특징 변수', '타당성(기술/편익)'으로 나뉘었습니다. 데이터 자체의 특성이 아닌 뜬금없는 단어가 하나 보일 것입니다. (기술적 타당성은 '수집 기법'에 대한 타당성이지, '분석 변수' 자체의 점검 항목이 아닙니다.)

04 생성 분석 변수의 전처리 방법으로 적합하지 않은 것은?

  • ① 데이터 정제
  • ② 데이터 통합
  • ③ 데이터 변환
  • ④ 데이터 삭제
[효빈위키 曰] Hint: 전처리 4총사(정제, 통합, 축소, 변환)를 반드시 외우시라고 강조했죠! 데이터를 줄이는 것(축소: Reduction)은 있어도, 막무가내로 '삭제'를 전처리 기법의 메인 카테고리로 부르진 않습니다.

05 빅데이터의 주요 품질 지표가 아닌 것은?

  • ① 편의성
  • ② 정확성
  • ③ 완전성
  • ④ 적시성
[효빈위키 曰] Hint: 데이터 품질 검증 4요소는 '정확성, 완전성, 적시성, 일관성'입니다. 편의점도 아니고 데이터 품질에 웬 편의성인가요.(...)

06 일반적인 데이터 분석 절차를 순서대로 나열한 것은?

  • ① 연구조사 → 문제 인식 → 데이터 수집 → 모형화 → 데이터 분석 → 분석 결과 제시
  • ② 문제 인식 → 연구조사 → 모형화 → 데이터 수집 → 데이터 분석 → 분석 결과 제시
  • ③ 데이터 수집 → 연구조사 → 문제 인식 → 모형화 → 데이터 분석 → 분석 결과 제시
  • ④ 연구조사 → 데이터 수집 → 문제 인식 → 모형화 → 데이터 분석 → 분석 결과 제시
[효빈위키 曰] Hint: 모든 프로젝트의 시작은 "도대체 뭐가 문제지?" 하고 '문제 인식'을 하는 것에서부터 출발합니다. 첫 단추만 잘 찾아도 1초 만에 풀리는 보너스 문제입니다.

07 분석작업계획 수립 절차로 적절하지 않은 것은?

  • ① 프로젝트 소요비용 배분
  • ② 프로젝트 작업분할구조 수립
  • ③ 프로젝트 정의서 작성
  • ④ 프로젝트 업무 분장 계획 및 배분
[해설 보충] 작업 계획 수립 절차는 WBS(작업분할구조) 작성 → 소요비용 배분 → 업무 분장 계획 배분으로 이어집니다. '프로젝트 정의서 작성'은 분석 계획(Plan)을 세우기 전 가장 앞단에 이루어지는 기획 단계의 산출물입니다.

08 다음 중 데이터 분석 과제 수행을 위한 필요역량으로 적합하지 않은 것은?

  • ① 데이터 거버넌스 체계 수립 역량
  • ② 도메인 이슈 도출 역량
  • ③ 분석 목표 수립 역량
  • ④ 프로젝트 계획 수립 역량
[효빈위키 曰] Hint: NCS 데이터 분석 절차(도메인 이슈 도출 ➡️ 분석목표 수립 ➡️ 프로젝트 계획 수립 ➡️ 보유 데이터 자산 확인)를 묻는 문제입니다. '거버넌스'라는 거창한 단어는 한참 뒤인 3과목(빅데이터 모델링/관리)쯤 가서 튀어나올 녀석이니 여기서 고르시면 됩니다.
